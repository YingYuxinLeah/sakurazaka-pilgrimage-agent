# 产品案例：櫻坂圣地巡礼路线规划 Agent

## 1. 用户与问题

目标用户是来日旅行或在东京活动的中国櫻坂46粉丝。他们能在粉丝整理地图中找到地点，却仍需要逐个打开地图、核对成员关联、计算交通时间并寻找餐厅。

核心 Job to be Done：当我只有半天时间并有明确区域、起点或成员偏好时，我希望快速得到一条能走完、顺路且信息来源清晰的巡礼路线。

## 2. 问题假设与验证方式

初始假设：圣地信息的主要障碍不是“没有地点”，而是“地点不能直接组成行程”。

低成本验证包括：分析现有 SakuMap 信息结构；用港区、六本木等真实任务走查；将原型发布给粉丝群和小红书用户，观察完成一次路线所需时间、补问次数、路线采纳率与失败原因。

当前阶段尚未把个人观察包装成规模化用户研究结论。后续应记录至少 5 位目标用户的任务过程与反馈。

## 3. MVP 范围

MVP 只解决东京区域内的一次步行巡礼规划：

- 输入区域、起点、时长、用餐需求和成员偏好；
- 从限定的 SakuMap 数据中筛选地点；
- 必要时在用户授权后补充普通餐厅；
- 计算步行路线并输出地图、时间与地点卡片；
- 支持多轮修改和重新规划。

暂不包含实时公共交通、营业状态保证、用户账户、收藏、UGC 地点维护和多人协作。

## 4. 需求与状态设计

必要字段：区域、起点、可用时长、是否用餐、是否限定成员。

成员偏好采用三态设计：未确认；已选择限定但等待姓名；已明确具体成员或不限。这个设计解决了“我想限定成员”被误当成完整条件、Agent 重复追问的问题。

切换区域默认视为新行程，清空旧起点、时间、用餐和成员；只有用户明确说“其他条件不变”时才继承，避免用旧条件规划错误区域。

## 5. 关键策略

- 数据可信：地点只能来自工具结果，空结果不等于现实中不存在；
- 授权优先：没有巡礼餐厅时，未经同意不能查询普通餐厅；
- 可恢复失败：地点过少主动建议放宽成员限制；服务失败明确区分“查不到”和“暂时不可用”；
- 成本可控：公开 Demo 每人每日 8 次、全站每日 120 次；
- 隐私最小化：仅保存日期、不可逆访客哈希和计数，不保存原始 IP 或对话。

## 6. 成功指标

北极星指标：用户在一次会话中生成可执行路线的比例。

辅助指标：平均补问轮数、路线生成耗时、空结果恢复率、用户修改条件次数、地点来源点击率、体验额度消耗与单次路线成本。

## 7. 产品经理贡献

本项目从用户问题定义开始，完成了任务拆解、MVP 裁剪、信息状态设计、Agent 与后端职责划分、工具协议、异常策略、评测案例、交互原型、真实网页与公开 Demo 的完整闭环。

## 8. 下一步

1. 用 5–10 位目标用户完成可用性测试；
2. 建立中文名、日文名与粉丝昵称词典；
3. 引入公共交通与营业时间，但保留来源与置信度；
4. 根据真实失败日志扩充评测集，而不是先增加功能数量。
